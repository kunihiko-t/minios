# MiniOS 設計書

## 1. 目的

MiniOS は、Rust と RISC-V 64 を使ってOSの基本要素を段階的に学ぶための小さなカーネルである。完成コードだけを提示するのではなく、後から読み返したときにも設計理由とハードウェア上の動作を追える日本語教材として整備する。

最初のマイルストーンでは、QEMU上で起動し、UART経由の対話シェル、例外・タイマー割り込み、物理ページ管理までを実装する。開発環境の確認、ビルド、実行、テストは統一した開発ハーネスから操作できるようにする。

## 2. 設計原則

- OSの中核機能は、学習対象としてリポジトリ内に実装する。
- 外部crateは、教材の本題でない処理に限って必要最小限に使う。
- Rust stableで再現できる構成を維持し、nightly固有機能には依存しない。
- 低レベル処理は小さなモジュールへ分け、依存方向と安全条件を明確にする。
- エラー時は停止するだけでなく、原因調査に必要な情報をUARTへ出力する。
- コードコメントは日本語で、構文の言い換えではなく設計意図、ハードウェア上の前提、`unsafe` の安全条件を説明する。
- 教材内のコマンドと期待出力は、開発ハーネスで継続的に検証できる形にする。

## 3. 対象環境

### 3.1 ホスト環境

主な開発環境はApple Silicon搭載macOSとする。Linuxでも同じCargoコマンドを使える構造にし、将来のCI実行を妨げない。

必要なツールは次のとおりである。

- Rust stable
- `riscv64gc-unknown-none-elf` Rustターゲット
- QEMU（`qemu-system-riscv64` を含むもの）
- Git

GoはMiniOSのビルドには使用しない。ホスト側ハーネスもRustで実装し、プロジェクト内の主要言語を統一する。

### 3.2 ゲスト環境

- ISA: RISC-V 64（RV64GC）
- QEMU machine: `virt`
- 実行モード: Supervisor Mode
- ファームウェア: QEMUから起動するOpenSBI
- CPU数: 1ハート
- メモリ: 128 MiB（`0x8000_0000..0x8800_0000`）
- 入出力: QEMU `virt` の16550互換UART

OpenSBIが使う先頭領域を避け、カーネルのリンク・ロードアドレスは `0x8020_0000` とする。UARTのMMIOベースアドレスは `0x1000_0000` とする。これらQEMU `virt` 固有のアドレスやメモリ構成を使う箇所は、定数名、コメント、教材で明示する。最初のマイルストーンではDevice Treeの解析を行わない。

## 4. スコープ

### 4.1 最初のマイルストーンに含めるもの

- OpenSBIからのカーネル起動
- 起動用スタックの準備とRustエントリポイントへの遷移
- UARTの送受信
- ログ、panic、例外診断
- RISC-Vの例外・割り込み処理
- SBIタイマーを利用したタイマー割り込みと稼働時間
- ビットマップ方式の物理ページアロケータ
- 固定長入力バッファを使う対話シェル
- ホスト単体テストとQEMU統合テスト
- セットアップ、ビルド、実行、検証を統一する `cargo xtask`
- 日本語の段階的ハンズオン教材
- 用語集、トラブルシューティング、アーキテクチャ解説、発展ロードマップ

### 4.2 最初のマイルストーンに含めないもの

- マルチハート対応
- 動的ヒープと汎用コレクション
- 仮想メモリ
- ユーザーモード
- プロセスとスケジューラ
- システムコール
- ファイルシステム
- ネットワーク
- Docker対応
- 実機対応

対象外の機能は発展ロードマップへ記載するが、初回実装に先行した抽象化は導入しない。

## 5. 全体アーキテクチャ

カーネルは `#![no_std]`、`#![no_main]` のRustバイナリとして構築する。最小限の起動処理とトラップ入口にアセンブリを使い、それ以外は原則としてRustで実装する。

想定するワークスペース構成は次のとおりである。

├── rust-toolchain.toml
├── README.md

│       ├── arch/riscv64/
│       ├── drivers/

│       ├── console/

│   └── superpowers/specs/

### 5.1 モジュール境界

#### `arch/riscv64`

RISC-V固有の起動、CSRアクセス、SBI呼び出し、割り込み制御、トラップ入口を担当する。他のモジュールへは、型付き関数と小さなデータ構造を通して必要な情報だけを公開する。

#### `drivers`

QEMU `virt` のUARTを担当する。1バイト送信、1バイト受信、受信可能状態の確認を基本操作とし、文字列整形やシェルの責務を持たない。

#### `console`

UART上の文字列入出力とフォーマット出力を担当する。カーネル各部がデバイスのレジスタ配置を知らずに診断メッセージを出せる境界を提供する。

#### `memory`

カーネル末尾からQEMUに指定したRAM末尾までをページ単位で管理する。ビットマップ方式でページの確保・解放・使用量集計を提供し、境界外アドレス、二重解放、未整列アドレスを検出する。

#### `time`

SBIタイマーの予約、割り込みごとの再予約、tick数と稼働時間の管理を担当する。シェルはこのモジュールの読み取りAPIを使い、CSRやSBIを直接操作しない。

#### `shell`

UARTからの行入力、編集可能な最小限の入力処理、コマンド解析とディスパッチを担当する。入力バッファは固定長とし、動的ヒープには依存しない。

## 6. 起動と実行時のデータフロー

1. QEMUがOpenSBIを起動する。
2. OpenSBIがカーネルELFを配置し、ハートIDを `a0`、Device Tree Blobのアドレスを `a1` に設定してSモードへ制御を渡す。
3. アセンブリエントリが割り込みを無効化し、静的に確保したブートスタックを設定する。
4. BSS領域をゼロ初期化してRustの `kernel_main` を呼び出す。
5. `kernel_main` がUART、トラップベクタ、物理ページ管理、タイマーを順番に初期化する。
6. 各初期化結果と自己診断結果をUARTへ表示する。
7. シェルがUART入力をポーリングしてコマンドを処理する。
8. タイマー割り込みが発生すると、トラップ処理がtick数を更新し、次のタイマーを予約してシェルへ復帰する。

トラップ処理は将来のユーザーモード対応を見据えて独立させるが、最初の実装ではカーネル実行中に必要なレジスタだけを保存する。最初から完全なプロセスコンテキスト構造は導入しない。

## 7. 対話シェル

プロンプトは `minios> ` とする。最初のマイルストーンでは次のコマンドを実装する。

- `help`: コマンド一覧と短い説明を表示する。
- `info`: MiniOS、RISC-V、ハートID、ビルド情報を表示する。
- `uptime`: 起動後の経過時間とtick数を表示する。
- `memory`: 管理対象、使用中、空きの物理ページ数を表示する。
- `clear`: ANSIエスケープシーケンスで端末表示を消去する。
- `shutdown`: SBI system reset拡張を通してQEMUを終了する。

入力はASCIIを基本とし、Enter、Backspace、表示可能文字を処理する。固定長バッファを超える入力は破棄せず、その行をエラーとして明示し、新しいプロンプトへ戻る。未知のコマンドには入力値と `help` の案内を表示する。

## 8. エラー処理と診断

学習時に失敗原因を観察できることを優先する。

- `panic` はメッセージ、ソースファイル、行番号、ハートIDをUARTへ出力する。
- 想定外トラップは `scause`、`sepc`、`stval` とトラップ種別を出力する。
- 初期化処理は段階名と成功状態を短く表示する。
- 回復不能な異常は診断後にSBI system resetを試みる。
- SBI終了が利用できない場合だけ、割り込みを無効化した待機ループへ入る。
- メモリアロケータは不正な解放を戻り値で報告し、テストでは具体的な失敗理由を検証する。
- QEMU統合テストはタイムアウト時にUARTログと実行コマンドを残す。

## 9. 開発ハーネス

ホスト側ツールはCargoの `xtask` パターンで実装する。追加のタスクランナーを必須にせず、macOSとLinuxで同じ入口を使う。

### 9.1 コマンド

- `cargo xtask setup`: Rustターゲット、QEMU、関連コマンドの存在と最低対応バージョンを検査し、修正方法を表示する。
- `cargo xtask build`: カーネルをRISC-V向けにビルドし、成果物のパスを表示する。
- `cargo xtask run`: カーネルをビルドしてQEMUを対話モードで起動する。
- `cargo xtask test`: ホスト単体テスト、クロスビルド、QEMU統合テストを順番に実行する。
- `cargo xtask check`: format検査、Clippy、ビルド、全テストを実行する。

終了コードは成功を0、検査失敗を非0に統一する。外部コマンドの失敗時には、コマンド名、終了コード、標準エラー出力を表示する。QEMUのパスは環境から探索し、見つからない場合は対応OSごとの導入方法を案内する。

### 9.2 再現性

`rust-toolchain.toml` でRustチャンネルと必要コンポーネント、RISC-Vターゲットを宣言する。依存crateは `Cargo.lock` に固定する。QEMUはハーネスで最低対応バージョンを検査し、実際に検証したバージョンを教材へ記録する。

## 10. テスト戦略

### 10.1 ホスト単体テスト

ハードウェアに依存しない処理を `no_std` 対応ライブラリ部分へ分離し、ホスト上で高速に検証する。

- シェルのコマンド解析
- 固定長行バッファ
- 物理ページの範囲計算
- ビットマップアロケータの確保、解放、枯渇、二重解放、境界エラー
- tickから時間への変換

### 10.2 クロスビルド検査

RISC-Vターゲット向けにカーネルをビルドし、リンカスクリプト、シンボル、`no_std` 制約の破損を検出する。必要な場合はELF情報を検査し、エントリポイントと主要セクションの配置も確認する。

### 10.3 QEMU統合テスト

テスト用ビルドをQEMUで起動し、UART上の構造化されたテストマーカーをホスト側ハーネスが読み取る。

- ブート完了
- UART出力
- トラップ処理
- タイマー割り込みの発生
- ページアロケータのカーネル内自己診断
- シェルコマンドの入力と応答
- 正常なSBI終了

統合テストごとに制限時間を設ける。失敗時は受信済みUARTログを省略せず表示し、ハングと明示的失敗を区別する。

### 10.4 CI

GitHub ActionsではLinux上にQEMUを導入し、`cargo xtask check` を実行する。ローカル専用の検証手順を別に作らず、ハーネス自体を単一の検証入口にする。

## 12. コメント方針

コメントは次の情報を優先する。

- ハードウェア仕様やABIによって必要になる処理の理由
- CSRの各ビットやMMIOレジスタを操作する意図
- `unsafe` ブロックが依存する不変条件
- 割り込みコンテキストで許可・禁止される操作
- リンカが提供するシンボルと実メモリの関係
- 固定値がQEMU `virt` 固有であること
- 単純化した設計と、一般的なOSとの差

変数名や構文を日本語へ言い換えるだけのコメントは避ける。公開APIには利用条件と失敗条件を記述し、コード変更時に誤った前提を残さない。

## 13. 完成条件

最初のマイルストーンは次の条件をすべて満たした時点で完成とする。

- Apple Silicon搭載macOSで `cargo xtask setup` が環境を正しく診断する。
- `cargo xtask run` でQEMUが起動し、`minios> ` が表示される。
- UART経由で全シェルコマンドが動作する。
- 例外・タイマー割り込みが動作し、稼働時間が更新される。
- 物理ページアロケータが確保、解放、集計、不正操作の検出を行う。
- panicと想定外例外が必要な診断情報を表示する。
- `cargo xtask test` がホスト単体テストとQEMU統合テストを実行する。
- `cargo xtask check` がformat、Clippy、クロスビルド、全テストを通過する。
- READMEから教材を順番にたどれる。
- 教材に記載したコマンドと主要な期待出力を実環境で確認済みである。
- 低レベルコードとすべての `unsafe` に日本語で理由と安全条件が記載されている。
