# 9. 物理メモリーとページ管理

## 学習目標

4 KiBの物理ページ、`__kernel_end`、ビットマップ方式のアロケーター、先頭適合、解放時のエラー、統計値の不変条件を説明できるようになります。

## 背景

Sv39を有効にする前でも、将来ページテーブルやヒープへ渡す物理RAMの所有権を、重複しないよう管理する必要があります。
QEMU `virt`のRAM全体である`0x8000_0000..0x8800_0000`にはOpenSBIとカーネルイメージが含まれるため、全域を未使用として扱うことはできません。

## 実装

[`FrameAllocator`](../../kernel/src/memory/frame.rs)は、`align_up(__kernel_end, 4096)..0x8800_0000`だけを管理します。
128 MiBには最大32,768ページがあるため、512個の`u64`、合計4 KiBのビットマップで表せます。
ビットマップ自体はカーネルイメージ内にあります。

`allocate`は先頭の0ビットを1にする先頭適合方式を使います。
`deallocate`は範囲外を`OutOfRange`、未使用ビットの解放を`DoubleFree`として拒否します。
`FrameAllocator::new`は、物理アドレス範囲の所有権を引き受ける`unsafe`な境界です。
アラインメント、空の範囲、ビットマップ容量は実装で検査できます。
一方、その物理範囲をOpenSBI、別のアロケーター、機器用のサブシステムなどがすでに所有していないことは、アドレス値だけでは判定できません。
呼び出し側は、成功時の全範囲が未所有かつ排他的であり、アロケーターが生存している間は別の所有者が取得しないことを保証します。

カーネルの入口では、OpenSBI領域`0x8000_0000..0x8020_0000`と、リンカーが示すカーネルイメージの末尾までを除外します。
残る`align_up(__kernel_end, 4096)..0x8800_0000`を、局所的な`FrameAllocator<512>`だけが管理します。
グローバルアロケーターと別のメモリーマネージャーは初期化しません。

払い出す`PhysFrame`は`Clone`でも`Copy`でもなく、`start(&self)`は所有権を消費せずにアドレスだけを読みます。
`deallocate`は`PhysFrame`を消費するため、安全なコードは同じ値を使って二度解放できません。
低水準のサブシステムから所有権を受け取る`PhysFrame::from_start`も`unsafe`です。
呼び出し側には、ページを排他的に所有し、同じアドレスを表す別の`PhysFrame`が存在しないことを求めます。
これにより、安全なコードから所有権の複製、偽造、重複範囲の作成はできません。

ビットマップは、`stats`について常に`total = allocated + free`を保ち、拒否した操作では値を変えません。
ただし、`unsafe`の規約を破って作られた別名参照や、ファームウェアとDMAなどアロケーター外部の所有状態は検出できません。
`OutOfRange`、`Unaligned`、`DoubleFree`は境界の誤用を調べる診断であり、`unsafe`の事前条件を肩代わりするものではありません。

## 実行と確認

```console
$ cargo xtask test memory
...
[MINIOS_TEST] memory: ok
```

ゲストテストは、異なる二つの整列済みページを確保し、一つを解放してから、同じページが再利用されることを検査します。
ホスト側の個別テストは、確保前、確保後、拒否操作後、解放後の`FrameStats`も具体的な値で確認します。

## よくある失敗

- リンカー領域との重複やファームウェアの破壊が起こる：開始位置を固定値にせず、`__kernel_end`から上へそろえます。
- 同じアドレスが二度返る：ビットマップの更新と、`unsafe`な範囲取得で所有権が重複していないかを調べます。
- `free`が減らない：`allocated`の更新と`total = allocated + free`を状態遷移ごとに確認します。
- 128 MiBの上端を超える：QEMUの`-m 128M`と`PHYSICAL_MEMORY_END`を同時に更新しない限り、上端を変更しません。
