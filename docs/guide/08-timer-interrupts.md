# 8. Supervisorタイマー割り込み

## 学習目標

QEMU `virt`の10 MHzタイムベースを100 Hzのティックへ変換する方法を学びます。
SBI TIMEの絶対デッドライン、STIEとSIEを許可する順序、アトミックなティックの読み方、テストが保証する範囲も説明できるようになります。

## 背景

S-modeは読み取り専用の`time` CSRから現在時刻を読めますが、M-modeのタイマーレジスターへ直接書きません。
次の発火時刻をOpenSBIへ依頼し、Supervisorタイマー割り込みの原因コード5をトラップハンドラーで受けます。
10,000,000 Hzを100 Hzで割るため、1ティックは100,000サイクル、つまり10 msです。

## 実装

[`time`](../../kernel/src/time.rs)は、初期化時とハンドラー実行時に`time`を読み、`now + 100_000`をSBI TIME拡張`0x54494D45`の関数0へ渡します。
過去のデッドラインへ追いつくのではなく、処理時点から次の10 msを予約します。
トラップの入口、最初のデッドライン、`sie.STIE`のビット5、`sstatus.SIE`のビット1という順に設定し、準備前の割り込みを避けます。

ハンドラーは`AtomicU64`を`Relaxed`順序で増やし、次のデッドラインを予約します。
現在はシングルハートで、ティックはほかの状態を公開するフラグではないため、このメモリー順序で十分です。
SBIエラーからの回復方法は定めていません。
最初の予約でも再予約でも、数値エラーを緊急用UARTへ出して異常終了します。

## 実行と確認

```console
$ cargo xtask test timer
...
[MINIOS_TEST] timer: ok
```

カーネルは3ティック以上を観測するとマーカーを出します。
この結果から、タイマー割り込みがハンドラーへ複数回入り、ティックが進んだことを確認できます。
ただし、短い観測だけでは、毎回新しい将来のデッドラインへ正しく再予約したことまでは証明できません。
保留状態の割り込みへ再び入るだけでも、カウンターが進む可能性があるためです。
再予約の正しさは、ハンドラーが`read_time + CYCLES_PER_TICK`を使うこと、SBIエラーを処理すること、間隔を空けた二回の`uptime`が増えることを合わせて確認します。

## よくある失敗

- タイマーテストが時間切れになる：`time` CSR、SBI拡張ID、STIEとSIE、原因コード5の分岐を順に調べます。
- すぐにトラップを繰り返す：絶対デッドラインではなく、相対値を渡していないか確認します。
- ティックは増えるが時間換算が違う：`TIMEBASE_HZ`と`TICKS_PER_SECOND`から100,000サイクルを再計算します。
- 3ティックのマーカーだけで再予約を断定する：テストで観測したことと、実装を読んで確認したことを分けます。

## 演習

`ticks_to_millis(250)`を手計算し、ホストテストの期待値2,500 msと照合してください。
次にQEMUのシェルで`uptime`を二回、1秒以上空けて実行し、差がおおむね1,000 ms以上になることを確認します。
